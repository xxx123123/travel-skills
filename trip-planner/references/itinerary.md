# 行程校验与快照

有明确日期和节点后，把要展示的主方案写成一份 UTF-8 JSON。`calendar`、`trip_id` 和 `events` 与 [日历导出](../../travel-to-ics/SKILL.md) 共用；`transfers`、`last_entry`、`budget` 和 `evidence` 不写入日历。

```json
{
  "calendar": "沈阳跨年旅行",
  "trip_id": "shenyang-new-year-2027",
  "events": [
    {"id": "checkout", "title": "酒店退房", "start": "2027-01-02T09:10:00+08:00", "end": "2027-01-02T09:30:00+08:00"},
    {"id": "flight-home", "title": "返程航班", "start": "2027-01-02T12:00:00+08:00", "alarm_minutes": [180]}
  ],
  "transfers": [{"from": "checkout", "to": "flight-home", "minutes": 50, "buffer_minutes": 90}],
  "budget": {
    "currency": "CNY", "limit": 2600,
    "costs": [{"label": "全员已支付机票", "amount": 1200}, {"label": "全程住宿", "amount": null}]
  }
}
```

- `events`：只放用户这一版会走、且可写进日历的节点。`start` 和 `end` 用带 UTC 偏移的当地时间；全天事项用日期。全天住宿不占用全天的游览时间。没有 `end` 的定时节点按一个时刻检查重叠；不要为了过校验猜结束时间。`last_entry` 用目标日期带偏移的时刻，事件的 `start` 此时应是预计到入口的时间；确实要核对但未查到时写 `null`。
- `transfers`：把影响可行性的交通段逐条列出，脚本只检查显式列出的段。按前项结束到后项开始计算，`minutes` 包含车程、停车、步行或接驳，`buffer_minutes` 是另需预留的时间（不填表示明确不加缓冲；待核时填 `null`）。时长没有可靠值时写 `null`，不可拿零分钟填空。若交通本身已写成占用时间的事件，用交通事件连接前后节点，避免重复计时。
- `budget`：有整趟硬上限才填写。统一币种、人群和范围，`costs` 每项填同口径必付金额；没核到实付时用 `null`，不要把日历低价、权益折算价或未核实的库存当成已知金额。单程和每晚预算在对应单项技能里判断。部分费用缺失时只报已知小计；小计已经超预算仍判冲突。
- `evidence`：只记录影响方案的关键事实，可放在顶层作为数组，用 `subject`、`source`（链接或可定位入口）、`checked_at`（带偏移）、`applies_to`（日期、班次、分店等）、`status`（已核实、参考、待核实）和 `basis`（如每位成人单程含税）记录。保留专项技能的原始口径，状态随日期或节点变化重查。脚本只查结构与可计算的约束，不验证来源或实时库存。

从本技能目录运行（Python 3.10+）：

```sh
python scripts/check_itinerary.py itinerary.json
```

输出含 `conflicts`、`pending`、预算小计及原文件的 `sha256`。退出码 `2` 表示已知冲突，应修正后重跑；`1` 表示文件或字段有误；`0` 表示已检查的约束中没有已知冲突，仍需在展示时说明 `pending`。例如上面的航班若改到 11:30，交通段会报冲突；若只是没查到住宿费用，会标待核。

展示从这份文件得到的方案和待核事项，保留原文件及当时返回的指纹。只有用户确认这版后，才向日历技能传原文件与该指纹。不重新抄写行程、不在确认后重存文件；时间或日程改变时保留已有事件 ID，按受影响的节点重查并展示新版。
